# 条件驱动的证据补全与反证检查

## 改进目标

在课程要求的历史 CVE 检索和按需仓库读取基础上，让 Agent 围绕漏洞成立条件取证，并检查当前代码中的安全条件是否能推翻初步假设。目标是改善成对识别效果和误报情况，同时记录分析成本。

检测内核已实现并通过合成联调，真实效果仍待课程数据与模块接入后验证。GitHub Bot 是后续交互入口，RAG 与仓库读取是课程基础能力。

## 历史案例如何提供线索

安晟毅从课程历史漏洞/修复对及其说明中整理：

- 漏洞成立需要哪些条件，例如长度可能超过剩余容量。
- 修复建立了哪些安全条件，例如在复制前检查长度上界。
- 每个条件对应的历史记录、函数片段或说明原文。

检索返回原始内容和这些条件。历史条件用于提出待核实问题；当前函数是否满足它们，由当前快照的证据判断。

## Agent 如何取证

以一个涉及 `memcpy(dst, src, len)` 的合成示例说明：

| 待核实问题 | 查询方向 | 可能的反证 |
| --- | --- | --- |
| 长度能否超过目标剩余容量？ | 分配位置、长度来源、指针偏移 | 存在有效上界约束 |
| 危险操作是否可达？ | 当前分支和调用方 | 超界输入提前返回 |
| 安全检查能否覆盖当前路径？ | 检查与使用之间的数据变化 | 检查后长度、容量或指针被改变，原反证不再成立 |

陈子星实现假设、条件与证据的关联。Agent 根据缺失条件选择下一次工具调用，主动寻找支持和反驳当前假设的证据，再决定结束或继续分析。史鹏飞的工具负责检索定位与代码读取，条件判断由 Agent 完成。

每个条件具有三种状态：

- `supported`：当前证据支持该漏洞成立条件。
- `refuted`：当前证据反驳该条件。
- `unknown`：现有证据不足。

条件引用报告中的证据标识。一个必要条件被反驳，只影响对应假设；一个假设被排除，不等于函数整体安全。`unknown` 也不自动等于无漏洞。成功检测仍输出课程要求的 0/1，理由说明证据范围；运行失败单独报告。

最终判定由 Agent 综合当前函数与快照证据作出，不按条件数量投票。输出 1 时说明可成立的漏洞路径及关键证据；输出 0 时说明已检查的主要假设及不支持其成立的原因。存在未知条件或相互矛盾的证据时，先在预算内继续核实；正常结束后仍未解决的，在理由中说明缺口、采用的证据及其对二元判断的影响。工具失败或预算耗尽导致分析未完成时返回执行失败。判定提示词与运行配置随实验记录，评测比较实际输出。

周德铭在报告中展示条件状态、解释和证据位置，用户可查看原始代码或历史来源。

## 效果如何验证

臧天心负责三组对照，组长在检测层提供对应配置：

| 方案 | 能力 |
| --- | --- |
| 函数基线 | 只输入待测函数 |
| 课程基础方案 | RAG + 自主按需仓库读取 |
| 条件方案 | 课程基础方案 + 条件补全与反证检查 |

主要比较后两组，用于检验新增机制；函数基线只作为实验参照，正式交付包含课程要求的完整 Agent。

各组使用相同模型、样本、解码设置和运行预算上限。记录 P-C/P-V/P-B/P-R、单样本误报与漏报、工具调用次数、token 用量和耗时；失败单独统计。token 用量取服务返回值，若不可获得则注明缺失。

两个使用 RAG 的方案采用相同历史数据和检索配置；条件方案额外使用由这些历史案例提取的条件。开发样本用于调试，最终测试前固定配置；样本配对、标签和各组结果仅在评测层汇总，检测会话相互隔离。

最终报告给出实际差异及典型成功、失败案例。效果提升是实验目标，不预设结论。
