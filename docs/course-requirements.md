# 课程要求与评分

依据课程 PPT《3. 函数漏洞检测智能体工具》（10 页）整理，后续课程通知由陈子星确认并更新。

## 必做能力

| 来源 | 要求 | 对应任务 |
| --- | --- | --- |
| 第 1、3 页 | 基于 LLM 的 C/C++ 单函数漏洞检测 Agent；补足安全知识和仓库上下文 | #2、#4、#5 |
| 第 4 页 | 历史案例检索、初步分析、证据不足时按需读取仓库、输出报告 | #2、#4、#5 |
| 第 5 页 | 基于提供的历史 CVE 数据建立 RAG；原始信息和 LLM 加工总结均可 | #2 |
| 第 6 页 | 读取调用方、被调用方、全局变量、类型、宏与辅助函数 | #3、#4 |
| 第 7 页 | 必须有图形化 UI，支持单样本和批量 `.jsonl` 输入 | #5、#6 |
| 第 4、7 页 | 界面展示检索记录和仓库读取记录，实时查看过程并接收报告 | #5、#6 |
| 第 7 页 | 报告包含函数 idx、是否有漏洞、判定理由、分析记录 | #5、#6 |

本组在上述要求之外增加[条件补全与反证检查](method.md)，并在检测闭环完成后接入 GitHub Bot。

## 历史知识与待测样本隔离

第 5 页允许历史知识库使用成对函数（漏洞版及修复版）、`cve_desc`、`commit_message`、`cwe`、`project`、`file_name` 等课程历史数据。知识库形式自由，可用原始信息，也可由 LLM 总结。知识来源仅限课程提供的数据集，不引入额外安全知识。

第 6、8 页对**待测样本**要求：

1. 一次只输入一对中的一个函数，不能同时提供漏洞版与修复版。
2. `target=1` 表示有漏洞，只读取修复提交的父提交仓库。
3. `target=0` 表示无漏洞，只读取修复提交后的仓库。
4. 不向模型提供 git diff 或两版本代码变更信息。

本组在准备层选择快照，标签留在准备和评测层；Agent 只接触当前样本的函数及单版本上下文。历史知识库允许的成对信息与待测样本的版本隔离不可混淆。

## 自主 Agent 与网络边界

第 10 页禁止将流程封装为 skill 直接调用 Codex、Claude Code 等商业代码分析 Agent，也禁止无自主决策的固定多步 LLM API 串行流程。必须使用 Agent 框架实现自主推理和工具调用。

除按 `commit_url` 获取指定版本仓库外，不提供其他网络搜索能力。模型和嵌入 API 可按课程参考路线使用，不代表允许检索网络上的漏洞答案。

开发者用 AI 辅助编写项目代码，与交付系统调用商业代码分析 Agent 是不同层面的行为；约束针对交付系统的检测能力。

## 评测规则

第 8 页说明测试集包含 150 对真实函数，共 300 条，已知字段为 `idx`、`commit_url`、`target`、`func`。字段具体类型及配对方式由 #1 与 #7 在数据接入时对照课程 `dataset/evaluate.py` 核对。

第 9 页按每对的预测统计：

| 类别 | 漏洞版预测 | 修复版预测 | 含义 |
| --- | --- | --- | --- |
| P-C | 1 | 0 | 正确区分两版本 |
| P-V | 1 | 1 | 两版本均判有漏洞，修复版误报 |
| P-B | 0 | 0 | 两版本均判无漏洞，漏洞版漏报 |
| P-R | 0 | 1 | 两版本完全判反 |

| 等级 | P-C 对数 |
| --- | --- |
| A | ≥ 30 |
| B | 25–29 |
| C | 20–24 |
| D | < 20 |

若 `P-R > P-C / 2`，最终等级下降一级，最低为 D。阈值使用严格大于，不含等于。

PPT 的 P-V 描述括注用词为“漏报修复版”；这里按其明确给出的预测组合说明为修复版误报。评测实现以提供的脚本为准，不自行更改课程指标。

## 数据取得后的确认项

- 历史数据与待测集的文件、字段、类型、配对信息和使用说明。
- 历史库与测试集的划分及是否存在相同样本。
- `commit_url` 的实际格式、父提交选择与代码所在版本的一致性。
- 课程评测脚本的输入输出、缺失结果处理和评分计算。

数据接入确认由陈子星负责，评分实现由臧天心负责。
