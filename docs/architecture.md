# 架构与数据流

这是实现前的设计基线，接口详见 [interfaces.md](interfaces.md)。运行中的检测 Agent 与辅助开发的 AI 编码工具分开讨论。

## 单样本数据流

1. Web 接收函数和仓库提交链接；批量入口接收课程 JSONL。
2. 准备层将课程标签映射为允许的仓库版本，生成不含版本语义的 `snapshot_ref`。Web 单样本输入修复提交链接，并明确选择该提交或父提交；Bot 定点输入使用显式指定的提交。版本选择只留在准备层。
3. Agent 接收 `idx`、`func` 和 `snapshot_ref`，先检索课程历史案例并分析已有证据。
4. 证据不足时，Agent 自主调用代码搜索、读取、定义或调用位置查询；工具只能访问绑定快照。
5. Agent 得出 0/1 判定，并返回理由、证据和工具记录。无法完成的任务返回显式失败。
6. API 通过 SSE 推送状态和操作记录，Web 显示完整报告。批量导出模块提取课程结果字段。

自主性体现在模型决定后续工具、查询内容和是否结束；不能仅在写死的节点序列中依次调用 LLM。框架可约束可用工具、访问范围与运行预算，但不替模型预先选择所有分析步骤。

## 隔离放在哪里

版本选择在准备层完成；Agent 工具使用一份单版本文件快照，而非含历史的 Git 工作目录。快照引用采用不透露 `target`、parent/fixed 等含义的标识。

准备层和评测层可以保存真实标签及配对关系。检测请求、模型提示、工具结果和模型可读文件只包含当前样本允许的信息。测试函数的修复消息、CVE 描述及另一版本不作为背景传给模型。

成员 A 维护历史知识库，允许课程历史案例的成对信息。成员 B 维护待测仓库读取范围。二者使用不同的数据用途，测试样本不能回流到历史知识库。

## 批量与评测

API 对每个样本建立独立检测上下文，不把前一个版本的分析、结果或对话传给下一个样本。同版本只读快照可复用，模型会话与报告必须按样本隔离。

成员 D 接收批量结果，核对 `idx` 覆盖及失败项，导出只含 `idx`、`prediction` 的 JSONL，并用课程脚本统计成对指标。组长负责调度与 API；成员 D 不另建一套检测 Agent。

## GitHub Bot

Bot 在 M3 验收后实施，复用准备层和检测 API。v1 使用显式请求中的提交链接、文件路径和函数名，抽取该快照中的函数，回复结果和报告入口。

Bot 可以在 PR 会话中发布报告，但不读取 PR diff、描述或讨论作为模型上下文。没有明确提交和目标函数时提示补齐输入，不自动扫描整个 PR。对 GitHub 的触发读取和报告写入属于外围集成；检测模型没有通用 GitHub 浏览工具。

## 本地存储与失败

课程数据位于 `data/`，快照和 RAG 索引位于 `storage/`，报告及评测产物位于 `artifacts/`；这些目录均不跟踪。凭据放在本地环境配置。

获取快照失败、仓库搜索不可用、模型错误和运行预算耗尽，都产生显式错误和已有操作记录。不得把失败当作良性结论或成功导出。运行预算和模型配置由 #5 实现时按实际服务确定并记入文档。
