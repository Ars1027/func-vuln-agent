# 架构与数据流

模块归属见 [团队分工](team.md)，字段与 API 见 [接口约定](interfaces.md)，分析策略见 [检测方法](method.md)。

## 检测流程

1. Web 接收函数、提交链接与版本选择，或课程 JSONL；准备层取得对应的单版本快照。
2. Agent 接收 `idx`、`func`、`snapshot_ref`，检索历史案例及其成立条件和安全条件。
3. Agent 提出当前函数的漏洞假设，将其拆成待核实条件，按证据缺口选择仓库工具。
4. Agent 核对支持证据与反证，更新条件状态，自主决定继续查询或输出结论。
5. API 通过 SSE 推送操作记录和条件更新，Web 展示报告与证据。评测模块生成课程结果并统计指标。

条件补全与反证检查由同一个 Agent 完成。框架限定工具范围和运行预算，模型决定查询内容、后续工具及分析终点。

## 数据隔离

准备层按标签选择课程样本的对应版本，输出不含标签语义的 `snapshot_ref`。手动输入明确选择该提交或父提交；Bot 使用显式指定的提交。

Agent 工具只能读取当前快照文件。标签、配对关系和版本解析信息留在准备与评测层，另一版本、Git 历史、diff 和待测修复说明不进入检测上下文。

RAG 使用课程历史案例，可提取历史漏洞/修复对中的条件；测试集与索引隔离。批量任务为每个样本建立独立模型会话。

## 运行与存储

开发和演示可在本地运行前后端；GitHub Bot 本地调试可接 webhook 转发。需要持续在线使用时，可将 Web、FastAPI、Agent 和知识库部署到 Linux 云服务器。使用模型与嵌入 API 时无需在服务器承担模型推理。

课程数据、快照/索引和运行报告分别放在 `data/`、`storage/`、`artifacts/`。获取快照、工具或模型执行失败时，保留已有记录并返回错误。
